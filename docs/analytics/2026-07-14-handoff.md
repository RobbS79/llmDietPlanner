## Consent behavior (important — explains "banner didn't show" / "no pixel found")

- Consent stored in `localStorage.mkt_consent_v1`. Banner shows ONLY until a first
  choice exists. To re-show it: clear that key (or use a fresh incognito window).
- Pixel loads only after consent === true. On a fresh load with no consent, the pixel
  correctly does NOT load → Pixel Helper says "No pixels found" until you accept AND
  reload. This is expected, not a bug — verified on prod.
- Anonymous visitors: consent persists in localStorage + rides the signup payload; no
  server POST (that was the 401 fix, already deployed). Logged-in users sync via
  `syncConsentToServer()` on login (Login.tsx + LoginSuccess.tsx).
- ⚠️ No consent-withdrawal path yet (no footer "Nastavení cookies" link). GDPR
  follow-up, deferred. See follow-up #4 in memory.

## Client-side forensics already done (so we don't repeat)

Verified live on prod via Playwright, returning-visitor path (consent pre-set, reload):
- `fbevents.js` present in DOM, `fbq` initialized, `callMethod` present.
- Internal fbevents state: pixel `1573455420886048` registered, `eventCount` increments.
- No CSP violations, no console errors. CSP allows connect.facebook.net (script) +
  www.facebook.com (connect/img).
- Caveat: an automated browser can't positively observe the `/tr` beacon leaving —
  modern fbevents batches via `navigator.sendBeacon` on pagehide, which Playwright
  can't capture. Pixel Helper on a REAL browser is the authoritative client check,
  and it went green. So client side is proven; only Meta-side ingestion is unconfirmed.
