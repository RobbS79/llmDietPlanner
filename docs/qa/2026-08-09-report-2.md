## Root causes (verified on prod after the run — supersedes the speculation above)

The in-run hypothesis (derived-tags union over-filtering the grounding pool) is **wrong** and is retained above only as the tester's working note. Two checks refute it:

- `required_tags_for_goal(goal 140)` returns `set()` — there is nothing to over-filter with.
- The corpus holds **297 published `vegetarian` recipes** out of 458, so a vegetarian filter could not empty the pool.

The three real causes:

1. **Blocker 2 is not actually fixed — the extractor is never asked for `dietary`.** `_SYSTEM_PROMPT_TEMPLATE` in `diet_planner/services/prompt_facets.py` defines the contract as `cuisines`, `wanted_ingredients`, `avoided_ingredients`, `styles`, `emphases`, `max_time_minutes`. There is **no `dietary` key**. `_coerce_facets` reads `data.get('dietary')` (prompt_facets.py:97) and commit 1c022fc persists that into `DietaryGoal.derived_dietary_tags` — but the model is never instructed to emit it, and did not in 3/3 live prod samples of the exact plan-140 prompt. So `facets.dietary` is always empty, `derived_dietary_tags` stays `None` (confirmed on goal 140, generated post-deploy), and every gate still has nothing to enforce. The persistence plumbing shipped without its input.

2. **Facet extraction intermittently dies on trailing output.** Live sampling of the plan-140 prompt on prod returned a valid contract object followed by a stray `}`; `json.loads` raised `JSONDecodeError: Extra data: line 12 column 1 (char 166)` and the whole extraction was discarded (1 of 3 samples; an earlier ASCII-folded pass was 2/2 empty). Empty facets make the overlay rescue-only, which is consistent with the 0/9 curated attach. Fix in PR #60 (`fix/facet-json-extra-data`) recovers the object; verified against the captured prod reply.

3. **The 500 is a pre-existing bug unrelated to either blocker.** `price_recipe` (`diet_planner/services/recipe_pricing.py:88`) does `ingredient.get('optional')`, but LLM-generated meals store ingredients as plain **strings** (`'pappudia tofu (#2153)'`) where curated meals store dicts. Reproduced on prod: `serialize_recipe_detail(Recipe 140:1:lunch:0)` → `AttributeError: 'str' object has no attribute 'get'`, raised from `RecipeSerializer.get_price_range` → `build_price_range` (`serializers.py:217`). Any plan containing generated meals 500s on every such meal; curated plans (138) are unaffected. Same family as the `_calorie_targets_from_days` str/dict crash from the 2026-08-05 run. Note the serializer computes `price_range` even though price display is disabled.
