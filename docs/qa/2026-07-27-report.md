## Refine chat v2 — defect summary (evidence)

1. **JSON leak into chat bubbles** (5/6 turns). Example visible text:
   `Rozumím, najdu ti něco jiného k obědu. Co bys řekl na kuřecí stroganov s noky? Je to syté a chutné jídlo.{"reply": "…", "candidate_id": "18944"}`
   Raw API: `reply_text` contains the concatenated prose+JSON, `candidate: null`, `research_job_id: null`.
2. **Candidate cards never surface** ⇒ the primary swap flow of the feature is unusable from the UI. Accept machinery itself is fine (verified via API).
3. **Phantom web search**: assistant claims it is searching the internet while no research job is created (no spinner, no poll). Only 1/6 turns actually invoked the tool; that job failed curation (honest failure copy — good) so no end-to-end web-recipe acquisition was ever demonstrated.
4. Suspected fixes: make `_parse_final` extract a trailing/embedded JSON object from mixed prose+JSON output, accept string `candidate_id`, and tighten the tool-use prompt so "search the web" narration is only produced after the `web_research` tool call.

## Hotfix verification vs. original defects

1. JSON leak — **fixed** (0 leaks in 4 turns; pre-fix it was 5/6).
2. Candidate cards unreachable — **fixed** (cards render; accept swaps the slot from the chat UI end-to-end).
3. Phantom web search — **fixed on the explicit web-request path** (job created, spinner shown, poll ran, result delivered). **Residual occurrence**: on the "něco s kuřecím masem" turn the assistant closed with "Zkusím pro vás najít něco vhodného na internetu" while `research_job_id` was null — no spinner, no job, dead end (verified: zero `/api/recipes/research/` polling requests). The prompt-level ban on search narration without a same-turn `research_web` call does not cover this corpus-miss → "I'll try the internet" phrasing.

## Follow-ups to ticket (non-blocking for this deploy)

- **A. Web-research relevance / fabricated source URL (P1).** The stored source URL was `toprecepty.cz/recept/47545-pravy-japonsky-ramen/` — that slug does not exist; toprecepty routes by numeric id and 301s to `47545-fazolovy-salat-zakladni` (a bean salad). The discovery step evidently emitted a fabricated slug+id; curation then faithfully processed the real id-47545 page, so the delivered content DOES match the link target, but it is unrelated to the user's request, and the bot framed it as success ("Našel jsem na webu recept…"). Honest-failure would have been the correct outcome. Recommend: canonicalize stored URLs to the fetched final URL, and add a relevance gate (query vs. curated title) before announcing success.
- **B. Residual phantom-search narration (P1).** See §3 above — corpus-miss turns can still promise an internet search without launching a job. Either force `research_web` in the same turn or rephrase to a question ("Mám to zkusit najít na internetu?").
- **C. Corpus search found no chicken recipes (P2)** despite chicken dishes existing in the corpus — investigate `search_corpus` recall (query language/embedding or exclusion logic).

No new console errors during the re-test (only the previously-noted stale-token 401s and the single earlier 500 on /api/auth/profile/ from the first run).
