# User Query Farm — Design

**Date:** 2026-08-17
**Status:** approved, not built
**Related:** [ingredient obtainability phase 2](../plans/2026-08-16-ingredient-obtainability-phase-2.md),
`docs/shopping-difficulty-report-2026-08-11.txt`, `docs/persona-test-prompts.md`

## The problem

We measure the corpus against itself. Phase 1 produced "458 published recipes,
164 fail the one-stop shopping bar" — an internal number. It cannot answer the
question that actually decides whether the product is worth paying for: **when a
Czech user asks for food, can we serve them?**

Retrieval does not draw from one pool of 458. Every query narrows it — slot
(`meal_types`), dish role, dietary tags, catalog mapping, prompt facets, and now
shopping difficulty. 458 recipes is ample in aggregate and can still be empty in
a specific cell; breakfast × vegan was already 7 of 26 in the Phase 1 report.
When a cell runs dry the planner either invents days (the hollow-day failure of
goal 133) or repeats dishes, which is the monotony behind the owner's "I would
not pay for it".

Phase 2's specialty gate is now live on prod while the substitution repair has
not run, so the pool is currently at its narrowest. We have no instrument that
tells us what that cost.

## Goals

1. Measure corpus coverage against **realistic user demand**, not invented
   prompts, and do it repeatably so before/after comparisons are meaningful.
2. Give the obtainability repair a quantitative pool gate: did substitution
   recover more than the gate removed?
3. Produce a **demand-weighted coverage** number that reframes corpus work from
   "add more recipes" to "close the highest-demand gaps".

## Non-goals

- Not a replacement for `/qa-prod`. That verifies a deployment in a browser;
  this measures corpus adequacy.
- Not a load or performance test.
- Not a curation pipeline. It reports gaps; filling them stays manual.
- Layer 4 (end-to-end generation) is specified here but deliberately deferred to
  a second implementation plan.

## Two axes, deliberately separated

What people want and how they type it are different datasets, and conflating
them is what makes hand-written persona prompts weak evidence — they encode our
imagination on both axes at once. The `Mám X` phrasing broke facet extraction in
production precisely because no test author had written it that way.

- **Demand** (which dishes) comes from external Czech data.
- **Phrasing** (how a request is worded) comes from real prod prompts.
- **Constraints** (diet, slots, day count) come from the persona set.

Queries are generated by crossing the three.

## Architecture

### Layer 0 — corpus mirror

`dump_curated_corpus` (read-only, run against prod) writes published
`CuratedRecipe` rows to JSON; `load_curated_corpus` loads them locally. Makes
every other layer local and prod-safe.

Side benefit: this removes the blocker that stopped the Phase 2 repair from
being rehearsed. The local DB has 21 recipes and 0 published, so the repair
could only ever have been run for the first time on prod.

The dump is **not committed** — a few MB of third-party-derived recipe text,
regenerable on demand. Written to the scratch directory.

### Layer 1 — demand index

`build_demand_index` produces `diet_planner/data/demand_index_cz.yaml`.

Sources, in priority order:

| Source | Role | Fragility |
|---|---|---|
| toprecepty.cz, recepty.cz popularity rankings | **discovery** — which dishes are actually sought | markup changes; fixture-tested parser |
| pytrends, CZ geo (`--with-trends`) | **weighting + seasonality** for terms already discovered | unofficial API, rate-limited; optional |
| Google Search Console / Seznam Webmaster | future first-party demand | not verified yet; contributes nothing today |

Only the recipe sites discover terms. Trends scores a candidate list — it cannot
enumerate queries — and Search Console needs verification plus weeks of traffic
before it says anything. Both sites are already credited sources in the corpus,
so scraping their public rankings is consistent with existing practice.

Schema per entry:

```yaml
- term: svíčková na smetaně      # dish name as published
  rank: 3                        # position in the source ranking
  source: toprecepty.cz
  trend_score: 78                # optional, 0-100, pytrends CZ; null when unweighted
  canonicals: [beef, cream]      # resolve_canonical() hits, for facet matching
  slot_hint: lunch               # inferred, advisory only
```

The committed snapshot is what the farm reads. A live fetch happens only under
`--refresh`.

### Layer 2 — phrasing corpus

`export_goal_prompts` reads real `DietaryGoal.prompt` values and emits
`diet_planner/data/prompt_templates_cz.yaml` — **templates only**, never raw
prompts. `prompt` is an `EncryptedTextField`; nothing personal may reach git.

```yaml
- template: "Mám {ingredient}, co uvařit?"
  observed: 4          # how many real prompts reduced to this shape
- template: "{diet} jídelníček na {n} dní"
  observed: 11
```

Scrubbing removes names, emails, digits outside recognised slots, and any span
that does not reduce to a known placeholder. A prompt that cannot be reduced is
dropped, not exported verbatim.

Constraint dimensions come from `docs/persona-test-prompts.md` (5 market
personas) and the 8 `PERSONAS` already in `selection_distribution_report.py`.

### Layer 3 — coverage farm (first implementation plan)

`diet_planner/services/user_simulation.py` owns query generation and verdicts:

```python
def generate_queries(demand, templates, personas, *, seed, n) -> List[SimulatedQuery]
```

`SimulatedQuery` carries persona, `prompt_cs`, extracted `PromptFacets`,
dietary tags, slot toggles, `num_days`, and the source demand rank.

`simulate_coverage` runs them with **no DB writes**, reusing the proven pattern
from `selection_distribution_report`: a `SimpleNamespace` goal (`pk`, `num_days`,
`breakfast`, `lunch`, `dinner`, `small_meals_per_day`, `snacks_per_day`,
`dietary_restrictions`) passed to `recipe_retrieval.select_recipes_for_plan`.

**Two facet modes, because two different things can fail.** A user's request can
be lost either because the corpus has no such dish, or because
`extract_prompt_facets` — which is a Gemini call — returned nothing. Downstream
these look identical: an unfilled slot. The farm separates them:

- **`direct` (default, LLM-free):** `PromptFacets` are constructed directly from
  the query's structured fields, exactly as `selection_distribution_report`
  already does. Measures the corpus in isolation. Deterministic, free, CI-safe.
- **`--extract-facets`:** runs the real extractor on the generated prompt text,
  caching results on disk keyed by prompt hash so a rerun costs nothing. Reports
  **extraction reliability** — the empty-facet rate per template — as its own
  metric.

The second mode instruments a known live defect: `Mám X` prompts return empty
facets roughly half the time, silently, so the overlay then ignores what the user
asked for. The farm is the first thing that would put a number on it.

Reported per query and aggregated:

- slots filled / total (`coverage`), and `gaps`
- **killer-filter attribution**: pool size after each successive gate — slot →
  role → dietary → mapping → specialty → facets — so a thin cell names its cause
  instead of just its symptom
- **demand-weighted coverage**, the headline:
  - `DWC@N` = share of the top-N demand terms the corpus can serve
  - reported strict and loose, because they answer different questions:
    **strict** = a published recipe whose diacritics-folded name tokens overlap
    the demand term by ≥ 0.6; **loose** = a recipe matching the term's canonicals
    via the existing `wanted_matcher` facet path
  - `DWC@20` (headline demand) reported separately from `DWC@200` (long tail)

Output: `docs/farm-coverage-<date>.txt`, in the shape of the existing shopping
difficulty report so the two read alike. The seed is printed in the header.

### Layer 4 — end-to-end farm (deferred, second plan)

`simulate_plans` generates real plans on the mirrored corpus for a sample of
queries, then judges them:

- **structural, deterministic:** invented days (`source != 'curated'`), repeated
  dishes, dietary violations, specialty ingredients that survived the gate
- **persona judge:** Claude reading as the persona — would this person cook this
  and pay for it? Reuses the `recipe_human_judge` pattern (advisory, fail-open,
  behind a flag and an Anthropic key).

Note the scope call: the obtainability spec deliberately parked appetite/appeal
as the *next* project. The persona judge steps into that territory on purpose —
it is the instrument that project will need — but it is not required to gate the
repair, which is why it is deferred.

## Robustness

| Failure | Behaviour |
|---|---|
| Ranking site markup changes | `--refresh` exits non-zero, keeps the previous snapshot. **Never** writes an empty index — a silently empty demand list makes coverage look perfect. |
| pytrends down or rate-limited | Downgrade to unweighted ranking; the run continues. |
| Prompt export meets un-reducible text | Drop the prompt. Never export raw. |
| Farm pointed at prod | `simulate_plans` refuses to run when `DATABASE_URL` resolves to the prod host. Hard guard, not a convention. |
| Judge unavailable | Advisory and fail-open, matching `recipe_human_judge`. |
| Two runs not comparable | Query generation is seeded; the seed is in the report header. |

## Testing

TDD per layer, no live network in any test:

- ranking parser against saved HTML fixtures
- scrubber against synthetic prompts containing fake PII
- `generate_queries` as a pure, seeded function — same seed, same queries
- `simulate_coverage` against a small fixture corpus with known pools, in
  `direct` mode; `--extract-facets` tested with the extractor mocked
- `simulate_plans` (Layer 4) with LLM and judge both mocked

## Phasing

**Plan 1 (next):** Layers 0-3. Ends with a committed coverage report measuring
the corpus as it stands on prod today — gate live, repair not yet run.

**Plan 2 (later):** Layer 4.

## Open question

The demand index measures what Czechs search for *on recipe sites*, which is not
identical to what they would ask a meal planner — a recipe site is dish-first,
a planner is week-first. This is the closest available proxy and it is honest to
say so in the report rather than present `DWC` as demand truth. Search Console,
once verified, is the correction: it reports what people typed to reach *this*
product.
